Требования к безопасности учетной записи:
  • Логин: только английские буквы, цифры и знаки _ . - (от 3 знаков)

  • Длина пароля от 8 символов
  • Заглавная (A-Z) и строчная (a-z) буква

  • Пароль не совпадает с логином и не содержит его
  • Пароли совпадают

Справочник по языку BPMN-as-Code (DSL) Спецификация
Структура файла диаграммы

Диаграмма BPMN-as-Code описывается простым кодом. Каждый процесс начинается с имени, затем перечисляются элементы (события, задачи, шлюзы) и задаются связи между ними.

process "Название бизнес-процесса" # 1. Объявление элементов (узлов диаграммы) start: req_started "Заявка поступила" task: check_data "Проверить корректность данных" service gateway: is_valid "Данные верны?" exclusive end: process_done "Процесс завершен" # 2. Описание связей (потоков управления) req_started -> check_data -> is_valid is_valid --[Да]--> process_done
Правила именования и синтаксиса
Элемент Правило Пример
ID узлов Латиница в snake_case, уникальные в рамках процесса order_received, check_balance
Названия В двойных кавычках "...". Для задач используйте глаголы "Согласовать счет", "Оплачено?"
Связи Стрелки ->, цепочки a -> b -> c start -> review -> gateway_ok
Условия Метки в квадратных скобках --[Текст]--> gateway_ok --[Да]--> approve_task
Комментарии Символ # в начале строки или после команды # Основной поток процесса
События (Start, End, Intermediate & Boundary)
Тип события Синтаксис DSL Описание
start start: id "Название" Стартовое событие процесса
start (message) start: id "Получен вебхук" message Старт по входящему сообщению / API
start (timer) start: id "Каждый понедельник 09:00" timer Старт по расписанию или таймеру
end end: id "Успешно завершено" Стандартное завершение ветки процесса
end (error) end: id "Ошибка авторизации" error Завершение ветки с ошибкой
end (terminate) end: id "Заказ отменен" terminate Принудительная остановка всего экземпляра процесса
catch catch: id "Ожидание оплаты" message Промежуточное ожидание внешнего события
throw throw: id "Отправка уведомления" signal Промежуточная генерация сигнала или события
boundary boundary: id "Таймаут 3 дня" timer on task_id Граничное событие на задаче (прерывание по таймеру/ошибке)
Задачи и распределение по ролям (Swimlanes)

Формат объявления задачи: task: <id> "<Название>" [<тип>] [by "<Роль>"] [loop [parallel|sequential]]. Указание роли by "..." автоматически группирует задачи в дорожки соответствующих исполнителей.

Тип задачи Синтаксис Семантика
user task: t1 "Проверить паспорт" user by "Оператор" Задача, выполняемая человеком через пользовательский интерфейс
service task: t2 "Списать баланс" service Автоматизированный сервис, веб-служба, обращение к БД или внешнему API
script task: t3 "Рассчитать скидку клиента" script Автоматический расчет или встроенный программный скрипт
send task: t4 "Отправить чек на email" send Отправка сообщения клиенту или другой системе
receive task: t5 "Ожидать подтверждение банка" receive Ожидание входящего подтверждения от внешнего участника
manual task: t6 "Упаковать посылку" manual by "Склад" Физическое действие без участия программной системы
businessrule task: t7 "Определить тариф по таблице" businessrule Принятие решения по таблице решений (DMN)
Подпроцессы, данные и примечания
subprocess: sub1 "Обработка претензии" by "Юристы" call: global_auth "Единая авторизация SSO" data: client_doc "Скан паспорта" datastore: crm_db "База клиентов CRM" note: sla_note "SLA согласования не более 24ч" on manager_review
Шлюзы и логика ветвления
Тип шлюза Синтаксис Поведение
exclusive (XOR) gateway: is_ok "Проверка пройдена?" exclusive Исключающее «ИЛИ»: активируется ровно одна из исходящих веток по условию.
parallel (AND) gateway: fork_steps "Запуск проверок" parallel Параллельное «И»: запускает все исходящие ветки одновременно. Для слияния используется парный параллельный шлюз.
inclusive (OR) gateway: options "Выбор опций" inclusive Неисключающее «ИЛИ»: запускает одну, несколько или все ветки, чьи условия истинны.
eventbased gateway: wait_event "Ожидание действия" eventbased Шлюз по событиям: процесс продолжает ход по той ветке, событие которой наступит первым.
Синтаксис стрелок и веток
# 1. Условные переходы из exclusive/inclusive шлюзов check_limit --[В пределах лимита]--> auto_approve check_limit --[Превышен]--> manager_review # 2. Поток по умолчанию (default flow) gateway_decision ==> default_action # 3. Парное разделение и слияние параллельных веток (fork & join) fork_check -> check_documents -> join_check fork_check -> check_credit_history -> join_check join_check -> issue_card
Пример 1: Согласование договора с условием Да / Нет
process "Согласование договора" start: doc_uploaded "Договор загружен" task: legal_review "Правовая экспертиза" user by "Юрист" gateway: legal_decision "Договор согласован?" exclusive task: sign_doc "Подписание договора" user by "Генеральный директор" task: rework_doc "Отправить замечания автору" user by "Юрист" end: doc_signed "Договор подписан" end: doc_returned "Возвращен на доработку" doc_uploaded -> legal_review -> legal_decision legal_decision --[Да]--> sign_doc -> doc_signed legal_decision --[Нет]--> rework_doc -> doc_returned
Пример 2: Обработка онлайн-заказа с параллельными ветками
process "Обработка интернет-заказа" start: order_created "Заказ оформлен" task: verify_stock "Проверить остатки на складе" service gateway: in_stock "Товар в наличии?" exclusive end: cancel_out_of_stock "Заказ отменен из-за отсутствия" terminate task: pay_order "Списать оплату" service gateway: fork_fulfillment "Запуск обработки" parallel task: assemble_box "Сборка заказа" manual by "Склад" task: print_invoice "Печать накладной и чека" service gateway: join_fulfillment "Заказ скомплектован" parallel task: courier_delivery "Доставка курьером" user by "Курьер" end: order_delivered "Заказ вручен клиенту" order_created -> verify_stock -> in_stock in_stock --[Да]--> pay_order -> fork_fulfillment in_stock --[Нет]--> cancel_out_of_stock fork_fulfillment -> assemble_box -> join_fulfillment fork_fulfillment -> print_invoice -> join_fulfillment join_fulfillment -> courier_delivery -> order_delivered
